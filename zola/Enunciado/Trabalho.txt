  OBS3: A implementação DEVE SER com pool de threads. 
        Isso EXCLUI usar "joins", por definição de pool de threads.

        - Então, nossa implementação com thread pool usa uma barreira 
          (foi assim na implementação dada para a redução paralela com 
            pool de threads)

        - Portanto quando foi dito na especificação 
          que o algoritmo de soma de prefixos 
          usaria PELO MENOS uma barreira, 
          significa UMA A MAIS para esse algoritmo
           (pois, a barreira do pool de threads eh do pool, 
            portanto não não eh do algoritmo de soma de prefixos)

       - Então teria duas no mínimo, Uma para o pool, 
             e Outra para a soma de prefixos

       - Ocorre que, deve ser necessário PELO MENOS mais
         uma barreira (a 3a barreira?) pois
         o seu algoritmo necessita garantir que a thread 0 (chamadora) 
         não retorne sem que todas as outras tenham completado a fase 2 
         da sua soma de prefixos. A não ser que voce tenha outro método para
         garantir isso!

         Portanto, ficou assim *flexibilizado* para uso de 3 barreiras :

           - Barreira 1 para o pool (OBRIGATORIA)
           - Barreira 2 para o algoritmo de soma de prefixos 
           (parece obrigatoria tambem, a não ser 
           que você use algum método com atômicos para eliminar essa barreira)
           - Mais uma barreira (a barreira 3) 
             Para garantir que todas terminaram seus cálculos

           OBS4: Eu disse também que SE alguem conseguir fazer com somente 2
            barreiras por algum método
           *mais Eficiente* (exemplo, atomicos ou coisa assim) ganharia 
           pontos MAS seria extra! Qualquer que seja seu método,
           ele deverá ser bem detalhado no relatório.

           OBS5: Mas de qq forma, 
           a implementação tem de ser com pool de threads 
           e manter a barreira 1 para o pool de threads, 
           nesse caso nao usar joins pois isso nao seria pool de threads

// será feita a soma de prefixos de 
//  um vetor de long long (ou seja, INTEIROS DE 64BITS) 
//  usando nThreads (definida via linha de comando)

// Para ESSE lab faremos:
//   a soma de prefixos será com a operação SOMA  (+)

// Funcionamento:
//  O programa deve funcionar para nTotalElements com nThreads 
//   Com: nTotalElements e nThreads obtidos da linha de comando
//   (assim como a versão feita em aula para a redução)
//  Utilização do programa:
//  usage: ./prefixSumPth <nTotalElements> <nThreads> <chunkSize> [-v]

    <chunkSize> 
    indica o deslocamento (NÚMERO DE ELEMENTOS NO CHUNK, i.e. stride)
    entre threads, assim voce vai especificar esse valor na
    linha de comandos, de modo que seu programa vai "tentar"
    reutilizar o cache para cáculos a cada <chunkSize> elementos.
    Voce deve experimentar e verificar, para a maquina de experimentos,
    qual eh o melhor valor para <chunkSize>.
    
    SE <chunkSize> == 0, isso será uma conveniencia para o utilizador
    do programa/função de Soma de Prefixos.
    Caso <<chunkSize> == 0, o programa/função deve calcular o <chunkSize>
    para que cada thread tenha APENAS 1 chunk, ou seja,
    nesse caso não estará tentando reutilizar o cache.
    Cada thread deve trabalhar com (aproximadamente) a mesma quantidade
    de elementos, a não ser a última thread, que pode ter ficado com menos
    elementos (se o total não for múltiplo do número de threads)
    
    -v  é um parâmetro OPCIONAL na linha de comandos
    Se o usuário colocar -v o programa DEVE fazer a verificação
    dos resultados rodando a funçao de verificação e imprimindo erros se houver.
    Se -v não for colocado na linha de comando
    o prograa fará apenas os calculos, imprimindo resultados de tempo e vazao.

COMO MEDIR tempo (e calcular vazao dentro do programa)       <<<=== VERSAO 1.6a
------------------------------------------------------

   Voce vai fazer um loop chamando a funcao paralela 100 vezes
   para a mesma matriz de entrada,
   vai iniciar o chronometro ANTES do loop e parar DEPOIS depois do loop
   e calcular/ reportar a MEDIA POR CHAMADA 
    
   Porem, como essa funcao eh inplace, voce deve manter DUA versoes dos dados
   de entrada:
     - voce inicializa os dados no vetor InputValues 
       (fora do loop, fora de medidas, no inicio do programa)
     - antes de CADA chamada da funcao paralela, 
       dentro do loop de 100 vezes,
       voce DEVE tirar copia (memcopy ou memcpy) do vetor InputValues
       no vetor Vector, e chamar a funcao parale NESSA COPIA
     - como o memcopy toma tempo nas medicoes,
       voce deve ter um chronometro EXTRA, vamos chamar de copyChrono, 
       e fazer start e stop no copyChrono, a cada memcopy.
     - depois do loop voce usa a funcao decreaseTime do pacote
       chrono, para descontar o valor do total de memcopies.
